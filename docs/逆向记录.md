## 复原的接口与功能路径

下表中的 VM 地址针对本样本 arm64 framework；插件地址另行标明。完整静态资料见 `analysis/agent-framework.md`、`analysis/agent-plugin.md`、`analysis/framework-arm64-disassembly.txt` 与 `analysis/framework-runtime-metadata.txt`。

| 功能 | 观察到的证据 | 宿主处理 |
| --- | --- | --- |
| 独立入口 | 导出 `JTStartCapture`（`0x2d764`）、`JTIsCapturing`、`JTCancelCapture`；`JTCaptureRequest` 类可加载。 | `CaptureEngine.m` 用 `dlopen` / `dlsym` 调用；加载前后核对所用 ObjC ABI。 |
| 最小依赖 | JietuFramework 的非系统链接依赖为 AFNetworking、CocoaLumberjack；两者可在新进程加载。 | 复制这三个完整 framework，保留 Versions、Resources 和符号链接；不复制 QQ 主程序、原插件 executable、MASShortcut 或 JTRecordSDK。 |
| 截图请求 | `JTCaptureRequest.init`（`0x1e364`）默认关闭 switch/customView；delegate/customView 为 weak。`startCaptureByRequest:`（`0x286bc`）枚举 NSScreen 并建立截图窗口。 | 自写宿主提供完成/取消 delegate，在主线程启动；不显示 QQ 的截图/录屏切换条。 |
| 选区与标注 | framework 含 JTCaptureView、JTEditView 及箭头、文本、马赛克等编辑类；截图窗口和工具栏由原引擎创建。 | 0.2.1 已在普通模式验证纯手动框选、框外重选、矩形标注和保存，其他标注工具仍待全面验证。 |
| 复制与保存 | `captureDidFinishWithImage:needSave:isHighResolution:`（`0x28cf8`）分别进入写剪贴板或保存路径，完成后返回 NSData/path。 | 宿主保留上一张图，校验回调图像和保存结果；`error=nil` 不能证明磁盘保存成功。 |
| 主题 | 资源通过 framework 的 `bundleForClass:` 定位；manager 初始化会 `resetTheme`。 | 每次重新获取 manager 后选择 `Jietu-theme`，复制完整主题资源。 |
| 生命周期 | `clean`（`0x2901c`）关闭窗口并清空全局 manager 单例。 | 不持续重用已清理的 manager；每次重新取得。 |
| 自动取消 | `addObserver`（`0x2a594`）订阅应用失去前台、隐藏、Space 变化；统一进入取消回调。屏幕数量变化也会取消。 | 普通模式保留原行为；`XCLIP_UI_TEST` 测试模式仅屏蔽失去焦点自动取消，避免 UI 自动化切换焦点中断截图。 |
| OCR、长截图、录屏 | OCR 路径依赖 QQ App Group 与通知；长截图独立路径尚未实测；录屏属于另一个 SDK。 | 隐藏并禁用工具栏 OCR/type 0 和长截图/type 2，不提供录屏入口。 |

核心调用约定由元数据和调用点交叉确认：

```objc
BOOL JTStartCapture(id request);
BOOL JTIsCapturing(void);
void JTCancelCapture(void);

- (void)captureRequestDidChange:(id)request;
- (void)captureRequestDidCancel:(id)request;
- (void)captureRequest:(id)request
 didFinishWithImageData:(NSData *)data
           saveToPath:(NSString *)path
                error:(NSError *)error;
```

这里是宿主实际使用的恢复声明，不能视作厂商公开 SDK。类型编码能验证调用布局，不能保证跨 QQ 版本的语义稳定。

插件还存在另一条独立模式路径：`canRunWithoutQQ` 读取 `settingkeyrunalone`，为 YES 时显示自己的状态栏；否则等待 DO 客户端，连接缺失后退出。NSConnection 服务名为 bundle ID 直接追加 `server`，远程 `requestCaptureScreen:` 接收 uint64 appId。当前实现直接加载 framework，没有使用这套原插件生命周期和 IPC。

## 自写宿主与权限桥接

宿主 [main.m](../Sources/XClip/main.m) 负责菜单栏、设置窗口、授权入口和回调结果；[CaptureEngine.m](../Sources/XClip/CaptureEngine.m) 负责引擎加载、接口检查、主题与功能入口控制。源码目录继续保留 `Sources/XClip`，产品名为 XScreenCapture，bundle ID 固定为 `milu.qqjietu`，本机安装路径为 `~/Applications/XScreenCapture.app`。

创建截图 manager 前，宿主替换当前进程内的 `+[JTCrashRqdManager startCrashReport]` 和 `-[MttWupManager startStat]` 为 no-op，以跳过已定位的上报启动路径。此处理不改写源 QQ 文件。**没有做全流程网络抓取，不能据此声称整个 framework 绝无网络行为。**

权限引导使用 [PermissionFlow 2.11.3](https://github.com/jaywcjlove/PermissionFlow)，锁定 revision `cb96db4bfd2342e8d8c56f2a7d51ca65b8aed6e2`。Swift 桥接导出 `XCPermissionGuide`，通过 `dlopen` 接入 AppKit；配置中文、当前 App URL 和屏幕录制面板，不主动请求辅助功能信任。

[Package.swift](../Package.swift) 要求 Swift tools 6.1、macOS 13。构建脚本按所选架构编译桥接，通用版本通过 lipo 合并；将 PermissionFlow 资源 bundle 和 MIT 许可放进 App，并删除桥接中的本机 Xcode 工具链绝对 rpath。资源迁移后仍可从 App 内定位，避免依赖 SwiftPM 构建目录。

## 0.2.0 历史实现与验证

[ShortcutController.m](../Sources/XClip/ShortcutController.m) 将全局热键注册与设置窗口的录制按钮分开。`XCShortcutKeyCode` 保存物理键码，`XCShortcutModifiers` 保存 AppKit 修饰位；缺省为 ⌘⇧2。新组合注册成功后才撤销旧组合并写入偏好，冲突或无效组合不覆盖原值。录制期间暂停全局注册，由本地事件监视器接收一次按键；Esc、点击其他位置、窗口或应用失焦时恢复原注册。显示字符通过当前键盘布局翻译，功能键与方向键使用明确名称和菜单等价键。

[ShortcutControllerTests.m](../Tests/ShortcutControllerTests.m) 的 19 项断言已通过，原始输出见 `analysis/self-test/shortcut-controller-tests.json`。测试在独立临时 bundle/domain 真实注册 ⌃⌥⌘F18，用另一 Carbon 注册占用 F19，验证冲突后的可用状态、字段和偏好不变；还覆盖无效组合、成功换为 F20、重建读取及析构释放。测试不创建窗口、不合成按键，退出时清理热键和独立偏好；**它不证明录制按钮、菜单同步或真实按键触发的 UI 流程已通过。**

[CaptureAppearance.m](../Sources/XClip/CaptureAppearance.m) 为选区与控制点提供颜色覆盖。设置窗口使用 NSButton 色块，点击显式打开系统 NSColorPanel；偏好 `XCSelectionBorderColor` 保存 sRGB `#RRGGBB`，默认 `#0099FF`。只覆盖 `JTCaptureView_SelectRect_BorderColor` 和 `JTCaptureView_ControlPoint_StrokeColor`，保留标注颜色。运行时检查相关 Objective-C 方法类型编码后才接入。

[ToolbarAppearance.m](../Sources/XClip/ToolbarAppearance.m) 在原 `JTToolbarButton.configAppearanceAndLayout` 之后替换已识别按钮的状态图片：采用黑色粗体 SF Symbols，分别生成普通、悬停、选中、按下、禁用态，保留原按钮事件和状态机。某个 symbol 不可用时保留该按钮原图；OCR 与长截图的禁用策略不变。

截图触发前，宿主从 CGWindowList 选择前台应用最前面的可见普通窗口；若宿主自身在前台，则用最近激活的其它应用。代码已移除原 220 ms 固定等待，改为下一次主队列事件循环启动，并设置截图窗口 `animationBehavior = NSWindowAnimationBehaviorNone`。这不意味着屏幕捕获耗时为零。

0.2.0 的 `XCPrepareInitialCaptureSelection` 接收 Quartz 顶部原点的全局窗口矩形，转换为 AppKit 坐标；跨屏时使用与窗口相交面积最大的单块屏幕内部分。当时 `XCSelectInitialCaptureWindow` 在原窗口建立后主动走 `didConfirmSelection`，建立编辑器与工具栏；该自动确认路径已在 0.2.1 移除。框外点击通过原命中测试识别，清理旧编辑器、缓存和选区状态后交回原 `mouseDown:` 继续框选，当前已有标注随重选丢弃，框内移动及控制点缩放继续使用原流程。未找到窗口时保留手动框选。窗口动画仅在截图相关窗口设置，不修改全局 NSAnimation 行为。

## 未验证边界

- 真实全局物理按键触发；快捷键冲突、Esc/失焦取消与恢复默认按钮的完整 UI 分支。独立测试已覆盖控制器冲突回滚，实际录制与重启持久化已验证。
- 颜色恢复默认按钮、工具栏全部状态、逐帧动画表现与响应时间测量。
- 矩形以外的全部标注工具、其他选区操作、磁盘失败处理、跨应用粘贴与撤销流程。0.2.1 普通模式已验证手动框选—重选—矩形标注—保存及 Esc 取消路径。
- QQ 不运行时连续多次截图，取消后重试及应用/Space 切换。
- 更广的 Retina 像素尺寸、多显示器、不同缩放比例和显示器热插拔；当前单次 `225 × 75 pt` 输出 `450 × 150 px` 已验证。
- macOS 13 及其他系统版本上的兼容性、真实 Intel Mac、系统升级后的旧截图 API 行为。
- 不同初始权限状态、拒绝后重新授权，以及 PermissionFlow 全部界面分支。
- QQ 更新后的 ABI/资源/功能语义变化；当前检查不能代替重新逆向。
- 全流程网络与文件访问行为；只对已定位的启动路径做了静态分析和抑制。

0.2.0 及更早版本采用本地 ad-hoc 签名；即使 bundle ID 保持 `milu.qqjietu`，修改二进制也可能导致既有 TCC 授权记录与产物不匹配。改名前曾移除旧屏幕录制条目、重新添加当时的 XClip 并重启，随后权限就绪且截图浮层可见。改名后也在用户完成 macOS 密码解锁后，移除旧条目、重新添加 `~/Applications/XScreenCapture.app` 并执行 Quit & Reopen，普通启动显示“截图已就绪”。这些步骤在当时环境有效，不能推断它们对所有系统版本或权限故障必然有效。0.2.1 已接入并成功使用本机 Developer ID 签署宿主，后续应保持同一身份；尚未进行公证、App Store 发布或可再分发授权评估。
